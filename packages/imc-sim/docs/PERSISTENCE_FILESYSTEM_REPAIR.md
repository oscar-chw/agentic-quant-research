# Filesystem admission after the ownership failures

Independent review found two failures in the initial0.4.0 build: resuming an operational database with an extra hard link mutated the outside alias, and verification accepted an unknown file under anchors. This repair changes only native filesystem admission; exact native code identity distinguishes the repaired0.4.0 wheel. Old persisted attempts are not migrated across that identity change.

Before opening operational files, admission walks a bounded grammar of the full attempt layout and rejects unexpected names, object types and link groups. Every ordinary operational/payload file must have exactly one link. The sole linked group allowed past this first stage is one scenario payload and one generation anchor, both with link count2 and the same device/inode, with both names inside the attempt. A third alias, an outside alias or a link between unrelated operational files refuses without unlinking or copying around it.

A second stage binds those possible pairs to OWNER and ARCHIVE_INTENT records from the existing audited operation chain. Actual anchors must equal the registered generation set; archived partials require their specific committed destination and directory/scenario identities. Product membership and bytes are checked against native derived payloads and the exact run plan. A known pre-owner product can still be inspected for its token, but resume refuses moving/reusing it. A present unregistered anchor refuses. During an active archive intent, the exact empty destination before rename and bound partial after rename remain valid transition windows.

Existing forensic completion receipts are bounded canonical records with exact kinds, field types, member sets, lengths and hashes. A receipt's mere filename does not qualify a generation. Partial publications also require committed archive ownership. Database/journal captures are retained with their self-contained byte-copy receipt before recovery can commit its RECOVERED reference; this preserves the capture-complete/acknowledgement-loss window. A referenced recovery capture must still exist, and incomplete captures remain preserved/refused. This cooperating-owner integrity contract does not authenticate wholly fabricated records and matching commitments against a malicious filesystem owner.

Ordinary load audits SQLite through immutable read-only access and checks filesystem relationships before opening a mutating connection. A recovery-needed journal still causes read-only RECOVERY_REQUIRED. Mutating recovery checks layout, link groups and existing forensic receipts before capture. If publication objects exist, it also proves their committed binding through immutable audit before capture; unreadable or ambiguous ownership refuses and preserves evidence. Only after the exact DB/journal copy receipt exists may SQLite recover. The recovered state/filesystem are rechecked before RECOVERED acknowledgement or economic advancement.

Internal capacity checks use the first admission layer so normal active SQLite journals, empty creation directories and scenario/anchor registration ordering continue to work. Public qualification uses both layers under the lifetime lock. No cap, economic transition, accounting rule, queue/cancellation policy or publication ownership exception was relaxed. Process-exit evidence remains distinct from untested power-loss, machine, multi-host and consumer behavior.
